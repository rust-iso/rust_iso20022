## Implemented scope

- `validate` parses through the core `ParsedMessage` abstraction and dispatches
  directly to validation bindings over the generated
  `pacs_008_001_08::Document`. It does not define a CLI message model or rules.
- The supported L2 binding reports all six independent cross-field failures in
  the invalid fixture. Unsupported generated message bindings return exit 5;
  they do not claim validity.
- L1 offline XSD validation is explicitly unavailable. Profile validation
  accepts only a complete `ProfileReleaseKey` and reports an exact but
  uninstalled release as unavailable. No latest/implicit release is selected.
- `catalog` and `versions` project the immutable code-generated core catalogue.
  The CLI contains no message list or version table.
- Every machine response uses JSON envelope schema version 1. Exit 4 means
  validation completed with errors; exit 5 means a requested capability or
  exact release is unavailable.
- Static diagnostics omit source XML and field values. The invalid fixture's
  `SECRET-OTHER-ACCOUNT` canary is absent from stderr and issue messages.
- `docs/cli.md` documents scripting, features, full release keys, exit codes,
  privacy, and the compliance boundary.
