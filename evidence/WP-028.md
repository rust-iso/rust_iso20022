## Status

**Done — T164–T170 complete.**

## Attack corpus and exact limits

`fixtures/security/xml/` contains minimized DTD, entity-expansion, XInclude,
non-UTF-8 declaration, unbound namespace, malformed structure, invalid Unicode,
deep nesting, oversized-input, and excessive-collection cases. The corpus uses
synthetic content only.

`ParseLimits::DEFAULT` is finite for input bytes, depth, events, elements,
attributes, per-event text, aggregate decoded text, and direct children per
parent. `tests/security/limits_matrix.rs` proves inclusive minus/at/plus
behavior for every field. `XmlStats::max_collection_items` exposes the largest
observed collection so collection accounting is measurable as well as
enforced.

CLI, MCP, and WASM tests independently prove that 8 MiB minus one and exactly
8 MiB reach core processing while 8 MiB plus one is rejected. The boundary
fixture splits text across bounded comment events so it tests the adapter input
limit without accidentally exceeding the separate 1 MiB per-event text limit.

## Entry-point and allocation audit

The audit found no XML or MT message entry point that bypasses a finite gate:

- core detect, metadata, tree, AppHdr, envelope, `from_xml`, generated
  `parse_auto`, and high-level `parse` all reach the shared XML preflight;
- CLI bounds reads before core parsing;
- MCP bounds protocol frames and accepts no file/network/shell inputs;
- both WASM surfaces call bounded core APIs;
- MT103, MT202, and MT940 conversions call the finite-default MT parser.

`docs/security.md` records exact limits, entry-point routing, inert
`schemaLocation` behavior, the no-network/no-resolver boundary, and residual
allocation behavior. XML preflight is streaming, but backend event strings and
generated model collections may allocate proportionally within the finite
limits. Generated deserialization is a second pass. Library-level JSON helpers
require the embedding application to bound untrusted input; CLI and WASM do so.

This closes R-PARSER for the current finite-default, no-network, typed-failure
claims. It does not claim formal verification or absence of undiscovered parser
defects; coverage-guided fuzzing remains WP-029.

## Privacy and unsafe logging

Whole-workspace canaries cover IBAN/account/name/address/reference/remittance/XML
across core errors and `Debug`, validation reports, default redaction, mapping
reports, CLI, MCP, and WASM. Mapping reports retain source tag/index/span and
classification but never source values.

WASM no longer installs `console_error_panic_hook`, which could print a
caller-controlled panic payload. Both surfaces install the core redacted hook,
which emits no payload, location, or backtrace. The dependency was removed.

Full values remain double-gated by the non-default `unsafe-full-logging`
feature and `unsafe` runtime acknowledgement. The feature-on test proves the
permit and prominent `UNSAFE_FULL_LOGGING_WARNING`; adapter manifests do not
enable the feature. `SECURITY.md` documents private vulnerability reporting,
supported versions, synthetic/redacted reproductions, and privacy disclosure.
